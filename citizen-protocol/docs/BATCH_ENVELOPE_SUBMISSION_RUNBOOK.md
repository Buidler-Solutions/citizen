# Batch Envelope Submission Runbook

This runbook demonstrates end-to-end usage of the runtime batch submit path:

- `POST /api/v1/envelopes/submit-batch`

It is designed for operators, SDK integrators, and relay services that want to
commit multiple signed envelopes in one runtime request.

---

## 1) What this path does

Batch submit accepts an array of `SignedEnvelope<LedgerEntry>` values,
validates each envelope/entry, applies each entry, then finalizes all accepted
entries in one block and returns per-entry receipts in a batch response.

Expected response shape:

```json
{
  "status": "accepted",
  "batch_size": 2,
  "receipts": [
    {
      "entry_id": "....",
      "namespace": "audit.procurement",
      "receipt": {
        "receipt_id": "....",
        "status": "Accepted",
        "finality": {
          "block_height": 1
        }
      }
    }
  ]
}
```

## 2) Prerequisites

From repository root:

```bash
cd /workspace/citizen
```

Start a local runtime node in a separate terminal:

```bash
cd citizen-protocol
cargo run -p citizen-node -- node.toml
```

Assumption for this runbook:

- Node API base URL: `http://127.0.0.1:8080`
- Namespace ruleset allows the sample entries (for example `audit.procurement`)

## 3) Prepare two signed envelopes

## 4) Submit the batch

```bash
curl -sS -X POST "http://127.0.0.1:8080/api/v1/envelopes/submit-batch" \
  -H "content-type: application/json" \
  --data-binary @batch.json | jq
```

Save response for later checks:

```bash
curl -sS -X POST "http://127.0.0.1:8080/api/v1/envelopes/submit-batch" \
  -H "content-type: application/json" \
  --data-binary @batch.json > batch-response.json
```

Extract key fields:

```bash
jq -r '.batch_size' batch-response.json
jq -r '.receipts[].entry_id' batch-response.json
jq -r '.receipts[].receipt.receipt_id' batch-response.json
jq -r '.receipts[].receipt.finality.block_height' batch-response.json
```

Expected:

- `batch_size == number of envelopes posted`
- all returned `finality.block_height` values are identical for this submission

---

## 5) Verify block contains all entries

Get the finalized height from first receipt:

```bash
HEIGHT="$(jq -r '.receipts[0].receipt.finality.block_height' batch-response.json)"
echo "$HEIGHT"
```

Fetch block:

```bash
curl -sS "http://127.0.0.1:8080/blocks/${HEIGHT}" | jq
```

Quick checks:

```bash
curl -sS "http://127.0.0.1:8080/blocks/${HEIGHT}" | jq -r '.block.entries | length'
curl -sS "http://127.0.0.1:8080/blocks/${HEIGHT}" | jq -r '.block.entries[].entry_id'
```

Expected:

- block entry count matches `batch_size`
- the `entry_id` values match those returned in `batch-response.json`

---

## 6) Verify each deterministic receipt endpoint

```bash
for RID in $(jq -r '.receipts[].receipt.receipt_id' batch-response.json); do
  echo "receipt_id=${RID}"
  curl -sS "http://127.0.0.1:8080/api/v1/receipts/${RID}" | jq
done
```

Expected:

- all receipts resolve
- each receipt finality block height equals the batch block height

---

## 7) Negative-path checks

### 7.1 Empty array should fail

```bash
echo '[]' > empty-batch.json
curl -sS -i -X POST "http://127.0.0.1:8080/api/v1/envelopes/submit-batch" \
  -H "content-type: application/json" \
  --data-binary @empty-batch.json
```

Expected:

- HTTP `400`
- body with error similar to `"batch must contain at least one envelope"`

### 7.2 Invalid signature mismatch should fail

Change one envelope so `payload.author != signer` or make signature empty.

Expected:

- validation error response
- no successful acceptance for that request

## 8) SDK demonstration (Node.js)

`sdk/nodejs` now exposes a batch submit helper:

```js
const result = await client.submitEnvelopeBatch([envelopeA, envelopeB]);
console.log(result.batch_size);
console.log(result.receipts.map((r) => r.receipt.receipt_id));
```

Use this for relay/aggregator pipelines that already hold signed envelopes.

---

## 9) Wallet/extension interoperability note

Current browser wallet direct submit path still posts single envelopes for
interactive UX. It now tolerates batch-style response shapes during receipt
extraction to avoid client breakage if upstream submit responses are batched by
an intermediate relay.

---

## 10) Operational guidance

- Keep batch size bounded at the relay layer to limit request payload size.
- Log `x-citizen-wallet-trace-id` and idempotency headers in edge services.
- Persist `batch-response.json` (or equivalent) for audit, replay, and receipt
  lookup.
- For multisig workflows, remember batching is transport-level grouping;
  multisig approval requirements are still enforced by namespace policy per
  entry.

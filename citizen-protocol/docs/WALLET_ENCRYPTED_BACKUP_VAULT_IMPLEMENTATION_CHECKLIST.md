# Wallet Encrypted Backup Vault Implementation Checklist

## Purpose

Define an implementation-first plan for adding a **wallet encrypted backup vault toolset** to the monorepo. The toolset is intended to protect wallet credentials generated by, with a primary deployment target of removable USB media:

- `wallet/cli`
- wallet browser extension surfaces

This plan targets a **multi-vault decoy model** (VeraCrypt-style behavior) with at least:

1. **Decoy vault** for low-sensitivity data and plausible-deniability workflows.
2. **Critical vault** for confidential wallet secrets and high-impact recovery material.

> Scope note: this checklist defines implementation checkpoints and acceptance criteria. It does not claim production security until formal review and threat-model sign-off are complete.

---


## Product Intent: VeraCrypt-Style USB Vault (Replicate + Innovate)

This initiative should replicate key VeraCrypt-style operating properties while adding Citizen-specific wallet recovery ergonomics:

- **Replicate**
  - Multi-slot encrypted vault behavior with decoy + critical separation.
  - USB-portable encrypted container workflows for offline custody.
  - Strong passphrase-gated access with tamper-detecting restore verification.
- **Innovate**
  - Wallet-aware backup scopes (identity keys, account keys, consent artifacts) with deterministic restore sequencing.
  - Builder/operator automation hooks through CLI JSON outputs and runbook-driven recovery checks.
  - Extension-safe encrypted export/restore paths aligned to browser runtime constraints.

> Security language constraint: avoid terms like “military-grade” in implementation and user docs. Use concrete primitives, parameter choices, and verified test outcomes instead.

## High-Level Design Constraints

- Governance-first and builder-first: integrate cleanly with existing wallet/runtime workflows and deterministic recovery expectations.
- Explicitly non-speculative: deliver practical wallet backup security, not token/economic behavior.
- User-custody aligned: encrypted backup material remains user-controlled; no plaintext credential escrow in protocol services.
- Backward-compatible migration path for existing wallet CLI and extension users.

## Checkpoint 2 — Cryptography and Vault Format

- [ ] Select password-based KDF parameters (Argon2id baseline) with environment-aware defaults.
- [ ] Define AEAD scheme (e.g., XChaCha20-Poly1305 or AES-256-GCM) and nonce/IV policy.
- [ ] Implement per-vault master key wrapping and per-object envelope encryption.
- [ ] Implement memory-hard unlock path and secure zeroization where feasible.
- [ ] Define vault file format:
  - [ ] global magic/version
  - [ ] slot table supporting `decoy`, `critical`, and future roles
  - [ ] authenticated metadata
  - [ ] rollback/anti-tamper counters
- [ ] Define corruption detection and deterministic error codes.

**Exit criteria**
- [ ] Crypto design reviewed against current repo wallet/off-chain encryption patterns.
- [ ] Test vectors committed for key derivation, encryption, decryption, and tamper failure.

## Checkpoint 3 — Multi-Vault / Decoy Capability

- [ ] Support creation of 2+ independent encrypted vault slots in one container or linked containers.
- [ ] Implement explicit role metadata (`decoy`, `critical`, optional `archive`).
- [ ] Ensure decoy and critical slots are cryptographically unlinkable from ciphertext patterns as far as practical.
- [ ] Implement access policy:
  - [ ] decoy passphrase unlocks only decoy slot
  - [ ] critical passphrase unlocks critical slot(s)
- [ ] Add optional duress-safe UX guidance (without false guarantees).
- [ ] Implement slot-level wipe, rotation, and passphrase update.

**Exit criteria**
- [ ] Demonstrated creation/unlock/rotation for decoy + critical flows in integration tests.
- [ ] Security review note explicitly states deniability boundaries and residual forensic risk.

### Implementation Status Notes (as of 2026-04-30)

- `wallet backup` CLI command group is implemented with: `init`, `add-slot`, `export-credentials`, `verify`, and `restore`.
- Vault schema scaffold `citizen.wallet.backup.v1` exists with role metadata for `decoy` and `critical`.
- `wallet backup init` now supports optional portable metadata (`--portable-label`) and records `created_at` for restore/runbook context.
- Backup export/restore path is wired to encrypted payload handling and checksum validation on restore.
- `wallet backup verify` supports role-specific integrity validation (`--role` + passphrase/env var) that decrypts slot payloads and re-validates checksum deterministically.
- CLI supports machine-readable output for `verify` and `restore` (`--json`) to enable deterministic operator automation pipelines.
- Wallet CLI tests now include backup round-trip recovery and tamper-detection assertions for checksum mismatch handling.
- Threat-model baseline document is now tracked in `citizen-protocol/docs/WALLET_ENCRYPTED_BACKUP_VAULT_THREAT_MODEL.md`; remaining work includes formal security sign-off and expanded operator runbook drills.

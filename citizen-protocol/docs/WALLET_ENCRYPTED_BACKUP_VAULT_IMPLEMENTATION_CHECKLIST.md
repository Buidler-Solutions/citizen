# Wallet Encrypted Backup Vault Implementation Checklist

## Purpose

Define an implementation-first plan for adding a **wallet encrypted backup vault toolset** to the monorepo. The toolset is intended to protect wallet credentials generated by:

- `wallet/cli`
- wallet browser extension surfaces

This plan targets a **multi-vault decoy model** (VeraCrypt-style behavior) with at least:

1. **Decoy vault** for low-sensitivity data and plausible-deniability workflows.
2. **Critical vault** for confidential wallet secrets and high-impact recovery material.

> Scope note: this checklist defines implementation checkpoints and acceptance criteria. It does not claim production security until formal review and threat-model sign-off are complete.

---

## High-Level Design Constraints

- Governance-first and builder-first: integrate cleanly with existing wallet/runtime workflows and deterministic recovery expectations.
- Explicitly non-speculative: deliver practical wallet backup security, not token/economic behavior.
- User-custody aligned: encrypted backup material remains user-controlled; no plaintext credential escrow in protocol services.
- Backward-compatible migration path for existing wallet CLI and extension users.

---

## Checkpoint 0 — Discovery, Threat Model, and Requirements

- [ ] Enumerate credential artifacts that need backup from CLI and extension (seed material, keypairs, metadata, consent receipts where relevant).
- [ ] Define attacker classes (device theft, cloud sync compromise, coercion, malware with filesystem access, backup corruption).
- [ ] Define plausible-deniability assumptions and limits for decoy vault behavior.
- [ ] Define supported backup targets (local filesystem only for GA-v1, optional cloud object-store adapter later).
- [ ] Produce STRIDE/LINDDUN-lite threat model appendix tied to wallet recovery flows.
- [ ] Define security and usability success criteria with measurable thresholds.

**Exit criteria**
- [ ] Requirements and threat model reviewed by wallet + crypto maintainers.
- [ ] Risks accepted/rejected and explicitly tracked.

---

## Checkpoint 1 — Monorepo Architecture and Package Layout

- [ ] Choose component location(s):
  - [ ] `wallet/backup-vault` (new shared library + CLI bindings), or
  - [ ] wallet crate integration under `citizen-protocol/crates/wallet` + UI adapters.
- [ ] Define stable data model crates/modules for vault headers, key-derivation config, slot metadata, and backup manifests.
- [ ] Define trait boundaries for storage backend adapters (filesystem first).
- [ ] Define interop contract for CLI and extension clients (common schema + versioning).

**Exit criteria**
- [ ] Architecture decision record (ADR) merged.
- [ ] Public interfaces versioned (`v1alpha1`/`v1`) with forward migration notes.

---

## Checkpoint 2 — Cryptography and Vault Format

- [ ] Select password-based KDF parameters (Argon2id baseline) with environment-aware defaults.
- [ ] Define AEAD scheme (e.g., XChaCha20-Poly1305 or AES-256-GCM) and nonce/IV policy.
- [ ] Implement per-vault master key wrapping and per-object envelope encryption.
- [ ] Implement memory-hard unlock path and secure zeroization where feasible.
- [ ] Define vault file format:
  - [ ] global magic/version
  - [ ] slot table supporting `decoy`, `critical`, and future roles
  - [ ] authenticated metadata
  - [ ] rollback/anti-tamper counters
- [ ] Define corruption detection and deterministic error codes.

**Exit criteria**
- [ ] Crypto design reviewed against current repo wallet/off-chain encryption patterns.
- [ ] Test vectors committed for key derivation, encryption, decryption, and tamper failure.

---

## Checkpoint 3 — Multi-Vault / Decoy Capability

- [ ] Support creation of 2+ independent encrypted vault slots in one container or linked containers.
- [ ] Implement explicit role metadata (`decoy`, `critical`, optional `archive`).
- [ ] Ensure decoy and critical slots are cryptographically unlinkable from ciphertext patterns as far as practical.
- [ ] Implement access policy:
  - [ ] decoy passphrase unlocks only decoy slot
  - [ ] critical passphrase unlocks critical slot(s)
- [ ] Add optional duress-safe UX guidance (without false guarantees).
- [ ] Implement slot-level wipe, rotation, and passphrase update.

**Exit criteria**
- [ ] Demonstrated creation/unlock/rotation for decoy + critical flows in integration tests.
- [ ] Security review note explicitly states deniability boundaries and residual forensic risk.

---

## Checkpoint 4 — Wallet CLI Integration

- [ ] Add commands for backup vault lifecycle:
  - [ ] `wallet backup init`
  - [ ] `wallet backup add-slot`
  - [ ] `wallet backup export-credentials`
  - [ ] `wallet backup verify`
  - [ ] `wallet backup restore`
- [ ] Support selective export (identity keys, account keys, recovery metadata, consent receipts).
- [ ] Enforce no-plaintext-on-disk policy by default (unless explicit override flag with warning).
- [ ] Add non-interactive flags for operator automation with safe prompts disabled only by explicit consent flag.
- [ ] Add deterministic JSON output mode for scripts.

**Exit criteria**
- [ ] CLI end-to-end backup/restore scenario documented and tested.
- [ ] Help text and warning copy reviewed for accuracy and safety.

---

## Checkpoint 5 — Browser Extension Integration

- [ ] Add extension UI flow for creating decoy + critical backup vaults.
- [ ] Add secure export bridge for encrypted payload creation (never raw secret exfiltration to page context).
- [ ] Add restore flow with integrity checks and clear conflict resolution strategy.
- [ ] Add UX affordances for backup freshness indicator and verification reminders.
- [ ] Add passphrase-strength guidance and recovery warnings.

**Exit criteria**
- [ ] Extension integration tests pass for create/export/restore/verify.
- [ ] Security boundaries documented for extension runtime and browser storage constraints.

---

## Checkpoint 6 — Recovery Safety and Operator Runbooks

- [ ] Define deterministic restore ordering when multiple backups exist.
- [ ] Add checksum + signed manifest verification for backup bundles.
- [ ] Add disaster-recovery runbook updates for wallet credential restoration.
- [ ] Add corrupted/partial-backup recovery guidance.
- [ ] Add key-rotation post-restore playbook.

**Exit criteria**
- [ ] Recovery drills executed for both CLI and extension scenarios.
- [ ] Runbook approved by maintainers responsible for wallet support.

---

## Checkpoint 7 — Testing Matrix and Quality Gates

- [ ] Unit tests: KDF params, AEAD envelopes, slot metadata parsing, manifest validation.
- [ ] Property/fuzz tests: malformed headers, truncated ciphertext, random bit flips.
- [ ] Integration tests: create 2-slot vault, export credentials, delete local wallet, restore, verify identity continuity.
- [ ] Adversarial tests: wrong-passphrase throttling behavior, tamper detection, replay/rollback attempts.
- [ ] Performance tests: unlock latency targets across workstation/laptop profiles.

**Exit criteria**
- [ ] CI includes backup-vault test suite and regression fixtures.
- [ ] No critical/high findings open from pre-merge security review.

---

## Checkpoint 8 — Documentation and Developer Experience

- [ ] Add implementation guide in `citizen-protocol/docs` for builders/operators.
- [ ] Update wallet generation/security docs with backup vault workflows.
- [ ] Provide “quick start” examples for CLI and extension recovery.
- [ ] Publish versioned vault format spec + migration strategy.
- [ ] Add explicit “what this does not protect against” section.

**Exit criteria**
- [ ] Docs reviewed for consistency with architecture baseline and wallet security docs.
- [ ] All user-facing commands and JSON schema examples validated against implementation.

---

## Checkpoint 9 — Rollout Plan

- [ ] Phase 1: feature-flagged alpha for internal maintainers.
- [ ] Phase 2: opt-in beta for selected builders.
- [ ] Phase 3: default-on for new wallet onboarding with migration prompts for existing users.
- [ ] Define telemetry/metrics (local-only or privacy-preserving) for backup success and restore confidence.
- [ ] Define rollback and incident-response procedure.

**Exit criteria**
- [ ] Release checklist signed off.
- [ ] Post-rollout validation report completed.

---

## Minimum Viable Deliverable (MVD)

For first mergeable implementation slice, require:

- [ ] 2-slot vault support (`decoy` + `critical`) in CLI.
- [ ] Password-based encryption with audited parameter defaults.
- [ ] Backup export + restore for wallet CLI credentials.
- [ ] Integrity verification command and deterministic error codes.
- [ ] Basic runbook and threat model document.

---

## Open Questions (Track Before GA)

- [ ] Single container with hidden slot semantics vs separate encrypted containers with coordinated UX.
- [ ] Hardware-backed key assistance (TPM/Secure Enclave/WebAuthn wrapping) as optional layer.
- [ ] Remote backup adapter requirements and trust boundaries.
- [ ] Enterprise policy hooks (mandatory periodic verify, escrow prohibitions, audit evidence).
- [ ] Long-term cryptographic agility strategy.
